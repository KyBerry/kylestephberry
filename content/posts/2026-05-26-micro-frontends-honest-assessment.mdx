Micro-frontends have been a recurring topic in frontend architecture writing for a few
years now. I've read a lot of the literature, dug into the Webpack Module Federation docs,
and built some small experiments to understand the tradeoffs firsthand. Here's my honest
read on when the pattern earns its complexity and when it doesn't.

## What the pattern actually promises

The core pitch is deployment independence: teams own discrete UI slices that they can
build, test, and ship without coordinating a monorepo release with every other team.
For organizations where frontend release cycles are a bottleneck, that's a real gain.
The secondary pitch — stack diversity, mix Angular and React in the same shell — is
usually a liability dressed up as a feature.

## What holds up

**Team autonomy is real at scale.** When a team can push a remote module to CDN
independently, release coordination disappears as a constraint. That matters when you
have many teams, each with their own cadence.

**Module Federation is genuinely capable.** Webpack 5's Module Federation and the
newer Vite/Rspack equivalents make runtime composition practical. The mechanics of
sharing a host application with dynamically loaded remotes work reliably.

## What the case studies leave out

**Performance budget ownership is fragmented.** In a monolith, the team collectively
owns the bundle. In a micro-frontend setup, each remote can grow independently. Without
explicit governance (bundle-size gates in CI, shared dependency version pinning), remotes
drift into independent performance debt that the shell application can't see.

**Shared authentication is awkward.** The shell handles the token; remotes need it.
Common approaches — a shared context object on `window`, a lightweight event bus, a
dedicated auth module — all add coordination surface that a monolith handles for free.

**Cross-seam integration testing is under-specified.** Unit tests live within each
remote. Integration tests that span the shell and multiple remotes require a local
orchestration setup that different teams configure differently. Contract testing (Pact)
is the principled answer; in practice it's frequently skipped.

<Callout type="note">
Module Federation's TypeScript type-sharing story requires manual coordination — type
stubs or the TypeScript plugin — to keep remote interfaces in sync. Budget time for this;
it's not automatic.
</Callout>

## My read

Start with a monorepo and a single framework. Extract modules into separately deployable
units only when you have a real, proven team-ownership boundary that justifies the overhead.
The performance, testing, and DX costs of micro-frontends are real. Earn the complexity
before you introduce it.

If you're inheriting a micro-frontend architecture, the patterns are learnable and the
autonomy benefits are genuine. Just go in with eyes open about where the seams are and
what governance they require.
