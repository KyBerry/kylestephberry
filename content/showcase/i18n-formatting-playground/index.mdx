Internationalization bugs hide easily because English is forgiving. A number can still read fine
with the wrong separators, a date can look plausible in the wrong order, and plural text can sound
close enough that the product ships with a small bug in every workflow. This playground makes those
differences visible.

The component uses the platform `Intl` APIs instead of formatting strings by hand: `NumberFormat`
for currency and compact counts, `DateTimeFormat` for the event time, `RelativeTimeFormat` for due
dates, `PluralRules` for label changes, and `ListFormat` for collaborator names. The controls are
small, but they cover the spots where most product UI cuts corners.

Arabic is here because right-to-left support changes layout, not just copy. The preview card sets
`dir="rtl"` for the Arabic locale, so alignment, inline ordering, and punctuation flow through the
browser's bidirectional text engine instead of a custom class toggle. That keeps the demo closer to
how a real app should behave.

The habit I'd push for is to treat locale as data. If a component receives a locale, hand
formatting to locale-aware APIs and let directionality participate in layout from the top of the
subtree.
